# 开发规范

参考 conning-room 的代码文件、文档存放和变更追溯规范，按 sceneweave 当前规模简化。本页是开发约定的单一归口；业务语义见[核心循环与角色职责说明](核心循环与角色职责说明.md)，实际实现范围见 [README](../README.md)。

## 1. 做事方式

- 想法与方案讨论先对齐目标和取舍；用户明确要求实施的任务直接执行，已确认的决定无需重复确认。涉及有争议的架构或改变业务语义时，先对齐受影响部分。
- 动手前读相关源码、调用方和设计依据；验证结果用于支撑判断，不能代替读代码。
- 一次改动围绕一个目的。优先直接、清楚的实现，按实际需要拆分模块、增加依赖和抽象。
- 当前用任务说明、Git 提交和必要的设计文档留痕。日常修改可在当前工作区完成、自测交付；暂不要求事项编号、队列状态流转、分级沙箱、独立验收或逐批实施日志。并行工作或确有隔离需要时再使用独立工作区。

## 2. 文件放哪

| 内容 | 位置 |
| --- | --- |
| Python 源码 | `src/sceneweave/`，内部职责划分见 README |
| 行为测试与假依赖 | `tests/` |
| 场景组装、演示与实验入口 | `examples/` |

源码不依赖测试、示例或开发脚本；业务规则集中维护，不在多个入口复制。运行数据、缓存、虚拟环境与真实密钥不进 Git。

## 3. 代码写法

- 使用 uv 管理依赖和运行命令，提交 `pyproject.toml` 与 `uv.lock`；运行依赖和开发依赖分开。
- 格式交给 Ruff：4 空格缩进、100 字符目标行宽、双引号、UTF-8 与 LF。
- Python 模块、函数和变量用 `snake_case`，类用 `PascalCase`，常量用 `UPPER_SNAKE_CASE`；名称表达职责与含义。
- 注释与文档用中文，解释原因和约束。简单代码无需模板式注释。
- 函数标注输入输出类型，跨模块消息使用明确的结构；避免共享可变状态。保持严格类型检查，第三方兼容例外局部说明。
- 外部输入和模型输出先校验；失败明确报错，不吞异常或静默返回成功。候选文本不直接变成世界事实。
- 按核心循环文档保持 World、引擎和角色的职责边界；Concordia 接口以锁定版本为准。
- 跨模块接口、消息、状态归属及时间表示遵循[模块交互契约](模块交互契约.md)。角色全量声明主动行为，World 维护实际状态与被动影响；不可用声明集合直接覆盖客观状态。
- 随机源、模型和外部服务在需要的边界显式传入，模块导入时不启动任务或调用模型。

### Concordia 接入、调试与运行语义（强制）

以下是相关组件和引擎的交付要求，必须随功能实现一起完成，不能作为可选优化延期：

- **必须适配本项目的剧情时间、行动持续性与结算语义**。Concordia 的默认循环、步进方式或实体调用顺序不得替代本项目约定；完整业务规则以[核心循环与角色职责说明](核心循环与角色职责说明.md)为单一依据。
- 剧情时间的接入须支持自定义剧情时钟与事件调度，并与模型耗时、调试暂停及其他墙钟等待分离；运行控制和 UI 须显示实际剧情时间及对应事件。
- 行动持续性的接入须遵循核心文档的全量主动行为声明语义，保留仍被主动维持的行动身份与进展，支持修改、撤回维持和新增。没有新增行动不等于空集合；合法空集合表示不再主动维持任何行为，不能清空被动过程或已发生效果。调试界面须区分主动声明、实际行动状态及被动影响，并可检查变更原因。
- 结算的接入须由 World 根据当时事实裁决、校验并提交，再发布反馈；提交、开始、完成、失败和未确认保持可区分。日志与界面须能对照行动尝试、结算结果和实际事实变化。
- **必须接入 Concordia 的组件日志与结构化日志机制**。System1/2/3、World 结算及引擎调度须可追踪，不能仅靠最终转录或零散文本日志定位问题。领域代码可通过接入层记录，保持原有依赖边界。
- 日志必须包含事件、角色、行动与组件标识（按适用范围）、剧情时间、触发来源、输入、输出、相关状态变化及错误；无行动、跳过和未确认结果也须明确记录。相关记录须能沿同一因果链查找，不能只记录最终成功文本。
- World 日志必须区分候选结果、校验结果、实际提交的事实变化和发布内容；角色的认知与意向单独记录，不能与客观事实混写。
- **必须接入 Concordia 的运行控制接口和可视化界面**，支持运行、暂停、继续与单步。当前已核对的接口包括 `StepController`、`StepData` 及引擎的 `step_controller` / `step_callback`；自定义引擎须适配这些接口并向界面提供实际步数据。
- 默认以一次事件处理为单步：事件落地、感知投递、本轮全部角色响应及统一登记完成后再进入下一事件。System1/2/3 的各阶段须能通过组件日志分别检查；控制接口不得接管角色内部编排，不能绕过本轮响应屏障。
- 暂停须在明确的安全边界生效，不打断 World 的事实提交。暂停等待不推进剧情时间、不计入墙钟运行超时预算；模型请求自身的超时另行处理。
- 调试查看到的角色内部状态和诊断数据不得自动进入其他角色的感知或世界事实。复现已记录的问题时须能使用保存的模型输入输出，不能仅依赖重新调用模型。
- 相关功能交付时必须验证日志可检索、界面收到真实步数据，以及暂停、继续、单步和上述三项运行语义符合核心循环约定；实际未接入的能力须明确标为未实现。

## 4. 验证

按改动选择检查，不要求每次全跑：

```bash
uv sync --locked                      # 初次安装或依赖变更
uv run --locked ruff format --check .  # Python 格式
uv run --locked ruff check .           # Python 静态规则
uv run --locked mypy                   # 类型与接口
uv run --locked pytest                 # 行为测试，可指定相关测试文件
```

- Python 改动检查格式、静态规则和类型；行为变化运行相关测试。纯文档改动核对内容、引用和 `git diff --check` 即可。
- 测试关注可观察行为和关键约束，不复制实现逻辑；有意义的缺陷修复补回归用例，不为低影响改动凑测试。
- 常规测试使用假模型和临时资源，不调用真实付费 API、读取真实密钥或修改用户数据。需要真实集成验证时单独说明前提和结果。
- 交付说明改了什么、怎样验证、还有什么限制。未执行、失败和未确认分别如实报告。

## 5. 提交与文档

- 提交格式为 `<前缀>: <中文主题>`；前缀使用 `feat`、`fix`、`docs`、`refactor`、`test`、`chore`。一个提交一个主题，必要时在正文写原因和验证结果。
- 只暂存本次相关文件，不覆盖其他人的改动；提交、推送及合并按用户授权范围执行。
- 用户已授权每完成一批可验证的进度后自动提交并推送；提交前完成相关检查，既存问题如实记录，不混入无关的在途改动。
- 每个事实或规则只维护一份：运行与实现现状归 README，业务语义归核心循环文档，开发约定归本页，AGENTS 只保留入口与工作提醒。
- 新文档按需在 README 或相关文档加入入口；移动、改名或删除时同步引用。不逐个登记源码文件，不强制状态头、文档地图或机器登记脚本。
- 行为、接口、运行方法有变化时更新对应文档。实现与设计不一致就明确差异，规划不能写成已完成；普通改动用提交留痕即可。
